# Postgres Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Move all app state, all tax data, the demo seed and the demo scenarios into Postgres, with the database as the source of truth, migrations, an import that never overwrites, a change log, and a Compose stack that starts from an empty machine.

**Architecture:** SQLModel on Postgres via `DATABASE_URL`; Alembic owns the schema (tables, constraints, triggers). `app/data_load.py` imports the built JSON into empty tables only. The engine keeps its maths and its dict shapes; `app/engine/data.py` holds the current `TaxData` and refreshes it from Postgres every `TAX_DATA_REFRESH_SECONDS`. Tests run on Postgres, each inside a rolled-back transaction.

**Tech Stack:** Python 3.10, FastAPI, SQLModel/SQLAlchemy 2, `psycopg[binary]` 3, Alembic, Postgres 17 (`postgres:17-alpine`), Docker Compose, pytest; React + Vite + Vitest + Playwright for the frontend part.

**Spec:** `docs/superpowers/specs/2026-11-13-postgres-design.md`

## Global Constraints

- The database is the source of truth after the first import. Nothing at runtime reads `countries.json`, `legal_forms.json`, `demo/seed.json` or `demo/scenarios.json`; only `app/data_load.py` and tests do.
- The import fills empty tables only; it overwrites only with `--replace <dataset>`, and records every run in `tax_data_load`.
- Every money column is `BIGINT`. Timestamps are `TIMESTAMPTZ`. No `rowid`, no SQLite code paths, no `PRAGMA`.
- Settings from the environment: `DATABASE_URL` (required), `DEMO_MODE` (default `true`), `TAX_DATA_REFRESH_SECONDS` (default `60`). Tests use `TEST_DATABASE_URL`, default `postgresql+psycopg://taxjar:taxjar@localhost:5433/taxjar_test`.
- API contract unchanged apart from `GET /api/demo/scenarios`. With `DEMO_MODE=false`, `POST /api/demo/reset`, `POST /api/simulate/incoming` and `GET /api/demo/scenarios` answer 404 in the single error format.
- The Acme why line stays `company sender · invoice in reference`; John still gets the question; the golden path passes after every task that touches the running app.
- skurbro's `backend/tools/tax_data/build.py` and `tests/test_data_build.py` are not changed.
- Test commands: `cd backend && .venv/bin/pytest -q` (needs `docker compose up -d db` with `DB_PORT=5433`); `cd frontend && npm test && npm run build`; golden: `cd frontend && npm run golden`.

## Review Focus

1. Two payments for the same currency arriving at once: balances and the Tax Jar stay consistent (no lost update) — Task 1, `test_concurrent_payments_keep_invariants`.
2. An amount above 32 bits (3 000 000 000 cents) is stored and read back exactly — Task 1, `test_amount_above_32_bits`.
3. A regime edited or deleted by hand while reservations still point at it: `GET /api/transactions` stays 200 and the reservation shows no breakdown — Task 4, `test_deleted_regime_does_not_break_transactions`.
4. The backend started against an unmigrated or empty database exits with a message naming the missing step, instead of serving empty screens — Task 7, `test_startup_refuses_unmigrated_database`, `test_startup_refuses_empty_tax_data`.
5. A restart or redeploy after a hand edit keeps the edit — Task 3, `test_second_import_keeps_an_edited_rate`.
